## v0.7.17(2026-09-11,两版同步)

**一墩里「结构对得上」一直要求逐字相同,于是一对主毙不掉「两张单」的撒牌。**
来自一次实战报修:主 ♥ 打 5,南甩 `♦Q + ♦J`,西出主 `♥8♥8` —— **结算判南赢**。

### 根因是一行比较

```js
function structMatches(cand, lead){
  const a=cand.type==='throw'?cand.comps:[cand];
  const b=lead.type==='throw'?lead.comps:[lead];
  return structSig(a)===structSig(b);       // 'pair' ≠ 'single,single'
}
```

主 `♥8♥8` 拆出来是 `pair`,南甩的 `♦Q+♦J` 是 `single,single`,签名不等 ——
西这一手在 `resolveTrick` 里被 `continue` **整个跳过**,南以 ♦ 的 top 收了这一墩。

正确的口径是**候选的组件可以拆、不能并**:一对拆得成两张单,所以盖得住;
两张单并不成一对,所以盖不住。这也正是同一副引擎里 `checkThrow` 那一侧
`canBeatComp` 早就在用的口径(它认「拖拉机压对子」)—— **两处本来就不一致**,这次统一。

新写法只需要把领出里的每一段**连对**(对子算 1 段、长度 L 的拖拉机算 L 段)
装进候选的某一段连对里;单张不用管,装完之后剩下的牌张数必然正好够。段数是个位数,回溯即可。

| 领出 | 候选 | 旧 | 新 |
|---|---|---|---|
| 甩 ♦Q+♦J(两张单) | 主 ♥8♥8(一对) | ❌ 跳过 | ✅ 盖得住 |
| 甩 ♦3♦3+♦9♦9(两个对子) | 主拖拉机 | ❌ 跳过 | ✅ |
| 甩 ♦Q♦Q+♦9 | 主 ♥8♥8+♥3 | ✅ | ✅ |
| 一对 ♦Q♦Q | 主 ♥8+♥9(两张散主) | ❌ | ❌ 不变 |
| 拖拉机 ♦7♦7♦8♦8 | 两个不相连的主对子 | ❌ | ❌ 不变 |

### 同一个根因的第二个症状:AI 明明毙得掉却不毙

`ruffThrow` 是 AI 专门用来毙撒牌的候选生成器。它按「领出几个组件就凑几个同型的主牌组件」
凑牌 —— 领出两张单,它就挑两张最便宜的主。凑完之后会再过一遍 `structMatches` 自查:

```js
const cl=classify(pick,trump);
if(!cl||!structMatches(cl,lead)) return null;
```

**挑出来的两张主恰好同点数时,`classify` 判成 `pair`,自查不过,整条候选被放弃。**
手里只有一对小主的人,明明毙得掉撒牌,AI 自己把这条路掐了 ——
报修里「毙牌不会毙、送分」说的就是这个。根因只有一处,症状有两个。

旧代码一行:

## 两处已知偏差修掉(2026-09-07)

第一届比完了,`RULES.md` §J 里压着的那两条到期。两条都动**合法性判定**,所以先量清楚
改动面再动手,而不是改完就算 —— 第一赛季的五份提交都是照旧口径写的。

### ① `decompose` 的贪心断链 → 分层

同一个 ordIdx 可能有不止一对(三门副级牌对全是同一个序号,无主局的四门级数牌对也是),
而它们对成链是**可替换**的。一趟扫下来的话,同序号的第二对当场把链切断 —— 于是
**手上多出一对同序号的对子,反而把本来连得上的链切短了**。

改成分层:同序号的第 1 对算第 0 层、第 2 对第 1 层……,一层一层地扫,层内 ordIdx
严格递增。最长的链必然落在第 0 层。**只有一层时(绝大多数手牌)和原来的一趟扫逐字等价**,
这也是为什么块②那 219 条自测一条没动就全过。

改动面量了三处 —— 这条偏差按规则书的说法会渗到 `classify`、`isLegalFollow` 的最长
拖拉机 `m`、`checkThrow` 的 `canBeatComp`:

| | |
|---|---|
| `decompose` 结果不同 | 同门牌里 **0.0083%**(82.8 万组样本里 69 组)|
| 其中「哪一对去凑链」的可替换差异 | 绝大多数 —— 组件形状一样 |
| `isLegalFollow` 的最长拖拉机 `m` | 主门手牌里 **0.0033%**(30 万手里 10 手)|
| `checkThrow` 甩牌成不成立 | **0 次**(23.9 万次判定);被拦时替出哪一组变了 1 次 |
| `classify` 的类型 / 长度 / top | **0 次**,而且是可证的:有同序号重复时组件数必然 ≥2,不可能塌成单一组件 |

所以真正会改判的只有跟牌义务里的「有长必跟」,万分之 0.33。

### ② 领出不成型不判罚 → 按「替出张数 × 5」罚

先复现:一个只会混门领出(♥5+♦7)的提交,20 场**全部抛 TypeError**,
被跑分器外面那层 catch 吞掉、场场作废,违规 0 次、罚分 0 分 —— 掀桌完全免费。

修在 `contest/referee.js`,**不在 build 里**:引擎的行为是对的(`classify` 见混门就该给
`null`,`checkThrow` 本来就只管甩牌成不成立),错的是裁判拿到 `lead` 之后没有过这一道。
现在领出也过一遍 `classify`,为 `null` 就替出裁判自己的领出、按张数罚,记作
`lead:不成型` —— 和「跟牌不合法」完全一样的口径。

修完同一个提交:**20 场全部判负**(0-20)。

这一条对合法对局是**零影响**,不是推理出来的:重跑 claude-opus-5 vs kimi-k3 的 40 场,
逐局记录和归档**逐字节相同**。

### 钉住

* `contest/ai-cheater.js` 的 `lead` 多了一路「领出混门」,裁判自测 38 → **39 项**,
  新的那条钉住 `lead:不成型` 真的被记下来
* §S5 向量 32 → **39 条**:三连对、四连对、同序号在低端(与贪心同结果)、
  没有重复时与贪心逐字等价,以及混门 `classify` 给 `null`
* 原先钉着**贪心行为**的那两条向量(「→ 两个二连对(而非一个三连对)」)是**反的**,
  跟着一起改 —— 自测向量钉的是当时的实现,实现改了它就从「保护」变成「阻挠」

### `--plays=DIR`

`league.js` 新开关,一对一个 `<A>__<B>.ndjson.gz`。**默认不开** —— 一季 55 MB,
而逐局记录才 3.7 MB,排名和赛报一个字节都用不上它。

它是逐局记录的**严格超集**。第一版不是:逐墩那一条只有发牌和出牌,谁坐庄、主是什么
得回头按下标去跟逐局记录对齐。改成超集的理由是那种对齐迟早会对错 ——
代价是 44 MB → 55 MB,值。

合并时踩到一次同名:逐局摘要里 `tricks` 是**墩数**(一个数),而逐墩那条里
`tricks` 本来是墩的数组,`{...摘要, ...逐墩}` 把墩数悄无声息地覆盖成了数组。
改叫 `plays`。这种覆盖不会报错,只会让下游读到一个形状不对的字段 ——
是靠「逐墩必须是逐局的严格超集」这条断言当场抓出来的。

手牌**不记**,因为算得出来(每家出掉的 25 张就是它拿到的 25 张;庄家那家是
「出掉的 + 扣掉的 − 底牌」)。工人自己落盘不走 IPC,先写 `.part` 再 `rename` ——
被杀时只会留下一个 `.part`,不会留下一份「看着完整、其实少一半」的记录骗过 `--resume`。
`--resume` 连逐墩一起对齐:断点有、逐墩缺或场数对不上的那几对重跑。

## 规则书吸收第二批反馈(2026-09-06,不进 build)

### 两张自测表在同一组输入上给了相反的期望

§S5「整场推进」表说 `[2,2]` 闲家上台升 1 级 → 队 0 到 3;「必打关卡」表说同样的输入

### 非法领出没有判罚,而且会把整场打断

有参赛者指出罚分表里缺「领出非法」这一行。查下来比缺一行更糟:

`lead` 返回的牌不在手上或形状不对,和跟牌一样罚(`resolveCards` 两边共用)。
但如果那些牌**确实在手上、只是凑不成合法牌型** —— 最典型是混门(♥5+♦7):

1. `classify` 返回 `null`;
2. `checkThrow` 见到 `null` 直接放行(它只拦「甩牌不成立」);
3. 跟牌方的 `isLegalFollow` 读 `lead.cards` 抛 `TypeError` —— **裁判自己崩在这里**。

跑分器每场外面有一层 catch,所以**这一场被作废**:不判负、不罚分,双方都不计这一场。
**等于给「打不过就掀桌」留了一条出路。**

本届五份提交一次都没触发(零崩溃),所以照 `decompose` 那条的处理:标成**已知偏差**、
写明修的方向(领出也过一遍合法性,`classify` 为 `null` 就替出裁判自己的领出、
罚「替出张数 × 5」)、排期在本届比完之后 —— 中途改判罚会让已跑的 258722 局
失去共同基准。§J 的已知偏差从一处变成两处。

### 「对子义务会造出无解局面」不成立

有参赛者报告 `isLegalFollow` 伪码里 `must` 缺一个 `⌊k/2⌋` 封顶,会造出「任何一手牌
都非法」的局面(他们量到约 2%),并写明「我没有利用它,因为裁判在这个局面下的行为
无法预测」。

查了:`must ≤ need = pairsInLead(lead)`,而任何领出都满足 **`2 × need ≤ 张数`**
(对子 1/2、拖拉机 L/2L、甩牌逐组件同理),所以 `must` 对总放得下 ——
先摆 `must` 对(占 `2×must ≤ n` 张),剩下的从本门补齐。
穷举 16388 个随机局面的**所有子集**,无解局面 **0** 个。

**他们因为这条不敢用奇数张甩牌,而那个武器根本不存在。** §S5 补了一行验算和三条向量。

## 联赛加断点续跑(2026-09-06,不进 build)

一届联赛几个钟头,而结果原本只在**最后**写一次 —— 中途掉一次进程就全没了。
今天真掉了一次(见上面「我自己弄掉了一次」)。

* `--resume` / `--ckpt`:每打完一对追加一行,再跑一次同样的命令就跳过已完成的对
* 逐局记录不再用一条长 gzip 流,改成**每一对自成一个 gzip 成员**追加进同一个文件。
  多成员是合法 gzip,`gunzip` 会把它们连起来;进程被杀也只丢最后那个没写完的成员
* 续跑时把两边对齐。记录是「先写记录、后写断点」,所以被杀时可能:
  记录有、断点没有(续跑会把这一对再打一遍,记录出现两份);
  或者断点有、记录只写了一半(这一对永远缺一块,而且没人会发现)。
  以「**两边都有、而且场数对得上**」为准 —— 只看有没有,会把写了一半的那一对
  静默收下。真发生了:抢救回来的第 10 对只有 545/600 场,靠这条被揪出来重跑
* `report.js` / `review.js` 读记录也带上 `Z_SYNC_FLUSH`,半截文件不再整个读不出来

`test/league-resume.js` 五条断言钉住:被杀之后已完成那几对的记录仍读得出来;
续跑的榜和逐局记录与一口气跑完的**逐字节相同**;记录场数对不上的那一对会被重跑。
进 `check-sync --full`。

顺带两条:

* 赛报加「用时」一节 —— 超时是全篇唯一的硬性淘汰条件,而联赛原本把量到的时间
  累加完就丢了,没有落进任何一份记录
* `contest-ops.md` 写清楚 `--jobs` 要按**带陪练的对数**给,不是按核数给:
  6 名选手里只有陪练那一个慢,它只出现在 5 对里。4 核 5 对时 `--jobs=4` 会剩一对
  排在最后单独跑,整整多一倍墙钟;`--jobs=5` 让它们一起跑完

### 超时门槛的分母原来是不可知的

原文:「总用时会公示,**超出基准选手 3 倍的提交不进决赛**」。这是全篇唯一一条硬性淘汰
条件,而**基准选手在截止之前不可知** —— 一条硬门槛变成了没法自查的东西。
上一届有人为了对表它花掉大半轮时间做纯提速,**那些工作对棋力零贡献**。

量了一遍,把数字写进手册:陪练每场约 **6.8 秒 CPU**(一方两个座位,开着收官搜索;
关掉是 1.6 秒)。一场约 6000 次决策,六成是 `onDeal`(中位数 5 µs),时间几乎全在
`lead`(中位数 3.7 ms、p95 72 ms)和 `follow`(中位数 0.8 ms)上。

门槛改成两条,都写死口径:整场总 CPU ≤ 20 秒(≈3× 陪练),单次决策 ≤ 2 秒
(陪练最慢的一次 0.21 秒)。计时用 `process.cpuUsage()` 不是墙钟(争用会把比值整个推高,
同一份代码能量出 2.8× 和 3.9× 两个数);按整场总和不按每次调用平均(会被占六成的
`onDeal` 稀释);丢掉前两场预热。

顺带一个对照:第一届两份提交实测每场 **0.23 秒**和 **0.07 秒** —— 都在门槛的 1/100 以下。
这条门槛是挡失控实现的,不该让人为它做优化。

### 抛异常怎么处理,原来一个字没写

按方法逐条列出来了:`onDeal`/`onRebel` 抛 → 当作没动作、罚 0;`discard` 抛 → 罚 40;
`lead`/`follow` 抛 → 罚替出张数 × 5。抛异常和「返回一手非法牌」罚得一样,
整场不作废、不判负。

并且写明:**不要在最外层无差别 `try/catch` 兜一手合法牌**。上一届真有人踩了 ——
裁判看到的是合法着法、不记违规、自查全绿,而策略层每一手都在抛,棋力掉了 0.57 级/局。
这是接口的失败模式设计让一类严重故障不可观测,值得单独警告。

### 罚分封顶的「满」是多少

原来写「罚到闲家得分归零(或满)」,「满」没有数字。写清楚:把闲家的**墩内得分**
夹回 `[0, 200]`,再按这个数算抠底翻倍 —— 所以最终总分**可以**超过 200,
夹的是墩内得分不是最终总分。

字段表里 `dealer` 和 `declSeat` 都写「庄家」,而 `declSeat` 读起来像「亮主的那一家」——
庄定局里那是两个人。没有改名(改了会打断已有提交),但加了警告并把两者的区别写开:
`dealer` 是发牌前定好的,`declSeat` 是定完主之后的;想知道谁亮的看 `curDecl.seat`。

### 其余

`onDeal` 一局问 100 次是**全桌**的总数、摊到一个人约 25 次(且发完补问那几圈手牌已完整);
`onRebel` **只问够格的家**,不用自己再判一次资格,而且比赛裁判是**开着**造反跑的;

**没有把它写成「有意为之」。** 规则书里按「已知偏差」标出来:本节的意图是最长链,
裁判当前是贪心版,**在裁判改掉之前照贪心版写** —— 判罚以裁判为准,写成最长链

## 比赛赛制定案(2026-08-31,不进 build)

第一版是「参赛者从基线 fork 起步、做增量改进」,现在整个转向:**参赛者拿不到我们的

排名也从「都对同一个陪练打」改成**联赛,两两都要对过局**。

### 空屋:只隔离引擎是不够的(第二次)

上一条已经修过一次「提交本身跑在宿主 realm 里」。这次发现更深的一层:参赛者和陪练
共用同一种 realm,而那个 realm 跑过块① —— 全局 `module.exports` 上就挂着整个
`ENGINE`,写一行 `globalThis.module.exports` 能把引擎连同 101 个 AI 内部函数整个
读出来。「自己照规则书写引擎」这条本来就废了。

现在参赛者走 `guestRealm`:**一行我们的代码都不加载**,只有 JS 内建和一个只能读
磁盘 .js 的极简 require,没有 `fs`/`process`/网络/npm。`selftest.js` 钉着这一条
(夹具会主动去摸,摸到就红)。

### 罚分:封在结果上,不是封在罚分上

口径是「裁判替你出了几张牌,就罚几张 × 5 分」,罚分记给对方队。

第一版没封顶,实测一个完全不合法的提交一场被罚一万五千分,把闲家得分推到极端值,
「每局净分」算出 +133 这种数(牌面上一局总共 200 分),**而且污染了跟它打过的
所有人的平均分**。第二版封罚分本身(每队每局最多 200)—— 还是没用,两队各罚 200
仍能让结算跑到 [-200, 400]。封在**结果**上才对:闲家最终得分夹回 [0, 200],
「罚到这局输光为止」。

两类不罚也不算违规:**甩牌被吃**(赌博输了,基线自己 240 场也输 9 次)、
**亮主压不过现在的**(牌是真有,只是不够大,判断失误不是 bug)。后者第一版每场
记上千次「违规」,把报表淹了。

### 自家选手要用显式白名单

判「哪些提交给我们的引擎」原本按 `contest/` 前缀,结果把
`contest/public/example/`(发给参赛者的模板)也判成自家 —— 模板在我们这儿能跑、
发出去就跑不了。改成只认包装了我们 AI 的那两个文件。

### 联赛

`contest/league.js`,多进程并行(每对一个工人,跨进程天然隔离)。规模是平方的:
17 名选手 = 136 对,单核 11 小时、8 核 1.5 小时。每对 30 副够 —— 排名靠对所有人的
累计战绩,单对噪声会被平均掉。

对局记录分两层:默认每局一行摘要(排名和申诉够用),`--log-hands` 才存每一手
(17 人全量约 2400 万手)。

### 发出去的那一份

参赛 repo:**https://github.com/ChannonTian/80fen-contest**。
`contest/public/` 就是它的全部内容:手册、规则书、提交模板、`submissions/`。

`public/RULES.md` 是**生成的**(`contest/gen-public.js`),对主 repo 的 `docs/RULES.md`

## 比赛基础设施(2026-08-30,不进 build)

**三份 html 一个字节都没改** —— 所以它不占版本号。新增 `contest/` 与
[`contest-ops.md`](contest-ops.md):让不同的人各写一个 AI,在同一套规则和同一个裁判下比。

赛制是**考全套 + 打级**:亮主、造反、扣底、出牌全由参赛者决定,一场从 2 打到 A
(平均约 30 局)。所有人对同一个基线打同一批种子,N 个人跑 N 次而不是 N² 次。

现成的东西比预想的多。这个项目本来就按「AI 只能通过 `view` 看牌桌」分层,
AI 决策路径里**零** `Math.random`/`Date.now`(核过块① 全段)—— 可复现是白送的;
非法输出早就有引擎兜底(`isLegalFollow` 不过退回 `genFollow`,`checkThrow` 不过罚
`forced`);`test/ai-h2h.js` 已经是「按座位分派两套 AI」的对照台。缺的是接口契约、
隔离、以及一条在 node 里跑得完的**完整**对局流水线 —— 原来的 h2h 只复刻了
「发完牌硬选最强的主」,亮主和打级整个不在里面。

### 搭的过程里被自己的测试抓到的三件事

* **只隔离引擎是不够的。** 第一版把引擎放进独立 vm realm,提交本身却用宿主
  `require()` 加载 —— 于是 `ai-cheater.js` 里一句 `Array.prototype.slice = ...`
  当场把裁判打穿。现在提交的代码也在 realm 里跑(`createRealm` 自带一个极简的
  CommonJS 加载器),realm 里没有 `fs`/`process`。**这不是安全沙箱**(vm 从来不是),
  是把「不小心」和「顺手作弊」挡住。
* **违规统计只数了前 50 条样本。** `onDeal` 每局调 100 次、瞬间占满明细上限,
  之后 `discard`/`lead`/`follow` 的违规只加总数不进样本,`summary()` 就看不见了。
  改成全量按种类计数,明细另存。
* **配对口径的坑又踩了一次。** 第一版跑分器只打逐场口径:两边跑**同一个** AI 时,
  它报出 ±20.4% 的胜率 SE 和 2.07 的级数差 SE —— 而配对口径下那两个数恰好是 0。
  同一个教训 `docs/notes/measurement.md` 写过一整页(逐副口径高估 2~3 倍),
  换个场景照样掉进去。已在 `docs/DESIGN.md` §12.4 记下「新写任何对照工具,
  先想清楚配对单位是什么」。

另外还改了裁判里两处**与界面块有意不同**的地方,都是为了公平:界面的亮主窗口只给
人类(AI 发完最后一张就不再决策),裁判给所有座位绕圈;界面 `aiLowRebel` 的循环是
`s=1;s<4`,**跳过座位 0**(人类的位置),纯 AI 对局里座位 0 也得被问。

### 赛制标定

* **无偏**:两边跑同一个 AI 时,配对口径的级数差与净分**恰好 0.00**,行为不同的种子 0%。
* **判别力**(120 种子,基线 vs「基线但从不低分造反」—— 只差一个布尔值):
  级数差 **+1.56 级/场**(SE 0.35,t=4.47)、每局净分 +2.42 分/局(t=3.93)、
  胜率 59.2%(t=3.11)、符号检验 p=0.0004。三个口径里**级数差最灵敏**。
* 顺带说明低分造反是真有价值的 —— 而基线在这件事上恰恰没有判断(界面里是掷骰子的)。
* 样本量:排名用 120 种子够;但这个项目历史上量到过的 AI 改动是 +0.56~+0.88 分/局
  那个量级,**120 种子分辨不了**,得跑 500 上下(约 75 分钟)。表在 `docs/contest-ops.md` §6。

### 甩牌被罚不是违规

标定跑完发现基线自己也"违规"了(240 场 9 次,全是 `lead:甩牌被罚`)。甩牌本来就是赌
没人吃得下最小的那一组,赌输是**规则内的结果**,不是契约违规 —— 混在一起报会让参赛者
以为自己写错了。已拆成单独一项计数。

### 顺带查实的一个死开关

`AIP.gateDamp`(「对手面临必打关卡 → 损失封顶」)在产品里**从未生效**:全项目只有
`aiDiscard` 里一处读取 `opt.gateAhead`,零处传入 —— 界面块调的是
`aiDiscard(hand, trump)` 两个参数。打级赛制第一次把关卡信息放进 `view`,
基线包装也第一次真的传上了。那个参数**从没被标定过**,现在是比赛里明摆着的可捡分。

  ——否则每墩还要点一下,托管就没有意义了。

按局生效(`G.auto` 挂在 `G` 上不持久化,`endRound` 里清掉,新的一局从你自己的手开始);

## v0.7.11(2026-08-21,测试版)

三条报障:两条手机竖屏的界面,一条 AI。

### 一出牌,顶部状态栏就被撑成两行(竖屏)

`#app` 竖屏那套网格的三行写成 `auto / 1fr / 0.6fr`。CSS 网格对**小于 1 的弹性系数**
有一条反直觉规则:`0.6fr` 只领走剩余空间的 0.6 倍,**剩下的 0.4 倍谁也不要**。
平时看不出来;一旦牌桌那行被自己的 `min-content` 撑到超过应得份额 ——
手机竖屏**一出牌**,`#msg` 多出「目前 X 最大 · 台面 N 分」这一行,正好越线 ——
这笔空转的余量就落到唯一的 `auto` 行(顶部状态栏)头上:`align-content` 默认 `stretch`,
状态栏被拉到 150px,两行字之间豁开一条,看着就是「一出牌状态栏就变两行」。

复现(Chromium,393×652,同一局面只差有没有出牌):状态栏 62px → **146px**,
右栏面板 179px → 93px。**这也解释了为什么它和屏幕高度有关**:844 高不犯,652 高必犯。

两处一起改:比例保持 1 : 0.6 不变,同乘 1/0.6 写成 `1.667fr : 1fr` —— 系数都 ≥1,
余量全部由面板吃掉;状态栏那行从 `auto` 改成 `min-content`,它不再是 `stretch` 的候选。
改后 600~844 高全程状态栏恒 62px,腾出来的空间归面板(652 高:93 → 177px)。

### 记录区的小牌看不清牌面

`--miniW` 是 `--cardW × 0.68`,这个比例照桌面端定的;竖屏 `--cardW` 只有 34~44px,
乘完剩 23~30px —— 四个角的字符互相挤住,`10♣` 尤其糊。两处改:
给 `--miniW` 一个 **32px 的绝对下限**(桌面端不生效,比例照旧),
小牌只留左上角点数 + 左下角花色(和手牌同一套语言,`#hand` 也只留左半边),
省下的宽度把字号从 0.44 提到 0.56。

### 「跟一对牌、垫其他花色废牌时,AI 还在凑对子」

**不是巧合,也不是凑对子 —— 是「一次排序取前 k 张」的副作用。**
`buildFollow` 断门那一支原来把 `discardSort(rest)` 排好序取前 k 张,而排序键是按
**整手牌**算的,取走一张之后局面就变了,一次性排序看不见:

* 副牌的 `ordIdx` 只看点数,♠9 与 ♥9 的键**完全相同**、结果里又紧挨着,于是被成对
  取走 —— 看着就是在凑对子(报障截图正是这一手);
* 贴分那一路的键只有「分值 + `globalIdx`」,既不认对子也不认门长,会把自家的对子
  整对丢出去,或者拆掉留个孤张(♠8♠8 + ♦8 里取走 ♠8 + ♦8);
* 两张分丢两门,哪一门也没短下去 —— 而**造缺**是垫牌的第一条道理。

改成 `fillPick`:逐张贪心,每取一张就按**剩下的牌**重算键。第二张时,被拆开的那张
不再算「对子」(少 14 的罚分)、已经垫过的那门又短了一张(≤2 时拿到造缺的 −5),
两者自己升上来 —— 三个症状同一个改法。真正的平局(两门都还长、点数又一样)再用
一个 0.5 的次序:同分就接着垫已经开始垫的那门。**没有引入新权重**,改的只是
「键该按哪一手牌算」;`discardGreedy=0` 一键退回。

配对口径的行为审计(200 局,同一批决策点上两种口径各算一次):
垫牌路 194 个决策点、16 个不同 —— 同门(造缺)103→119、两门各一张 57→44、
同点不同花 23→20;贴分路 121 个决策点、13 个不同,「拆自家对子」14→12。
场景库补 I1 / I1b / I2 / I1c 四条(含「另一门只剩单张时该垫单张」的对照组 ——
这个修法很容易滑成「一律往同一门垫」)。

同桌配对对照(2400 副 = 1200 种子 × 交换阵营,新版 vs `discardGreedy=0` 的自己):
**+0.17 分/局 ±0.15(t=1.14),符号检验 p=0.86 —— 在分辨率之下,读作打平。**
两版行为不同的只有 131/1200 个种子(10.9%),其余种子配对差恒为 0、不贡献信息。
按 `docs/notes/measurement.md` 的规矩记账:这一条**不是**靠聚合尺子成立的,
靠的是行为审计 + 第一性判据(排序键该按取牌之后的手牌算),尺子只用来确认它没变坏。

### 新量具:同桌对照的 SE 一直在高估 2~3 倍

`ai-h2h.js` 交换阵营的两副是**同一副牌**,牌运在它们之间严格反相 ——
两版完全一样时一副 `+d`、另一副必然 `−d`。旧代码把这 2N 副当成 2N 个独立样本求方差,
于是「净胜恒等于 0」和「SE = 2.76 分/局」可以同时出现:那 2.76 全是牌运,
而牌运在配对里是**恰好抵消**的。

改成配对统计量 `D=(d₀+d₁)/2`(先合并同一种子的两副,再对种子求 SE)。
空跑的 SE 从 **2.76 变成精确的 0.00** —— 恒等式级,不是「接近 0」。

同一批 1400 副数据,两种算法:

| 对照 | 净胜(相同) | 逐副 SE/t | 配对 SE/t |
|---|---|---|---|
| 测试版 v0.7.10 vs 正式版 v0.7.8 | +2.13 | 1.12 / t=1.90 | **0.47 / t=4.56** |
| `throwBossSubset` 单开关消融 | +0.91 | 1.12 / t=0.82 | **0.35 / t=2.61** |

第二行是验收:这条开关以前靠 **16 批 22400 副**才凑到 +0.88 ±0.28(t=3.09),
中途一度只有 t=1.30,差点被当噪声丢掉;配对口径**一批 1400 副**给出 +0.91 ±0.35。
数值对得上,成本差一个数量级。同一批数据在逐副口径下是 t=0.82,会被判成「量不出来」。

**均值两个口径完全相同,只有 SE 变** —— 以前的结论都是在被高估的 SE 下做的,
都偏保守,不会有哪条被推翻。工具两个口径都打,旧口径留着和历史数字对得上。
另外配对之后每个种子就是一个独立读数,符号检验不必再等「多批合并」,直接内置
(200 种子时 t 才 2.09,符号检验已经 p=0.0025)。

这条对应 `docs/DESIGN.md` §10.6(j)。原计划是「双明手当控制变量」,动手才发现排在它前面的是
这个更基础的错误;双明手因此降级(108 张牌的完全信息解本来也算不动)。

## v0.7.9(2026-08-18,测试版)

**「已知下家断门,还把分贴过去」—— 8 条报障的共同根因是一处量纲不同步。**

需求列表里这一簇有 8 条(已知对手断门还领出/主动贴分、已知下家断门跟废送分、

我不是末家 → 身后有对手在这门**已知断门** → 我这一手加了分 → 被那个断门方毙走。

根因在 `scorePlay`:

```
gain = X.ptsTable + my + laterPoints(...)   // 含我要贴的分
p    = pTeamWin(...) -> X.certainty         // 贴分**之前**算好的
```

而 `pSurvive` 的已知断门分支对台面分是敏感的 —— `(ptsTable>0 ? 0.80 : 0.35)`。

### 稳拿这墩时,该把「留着也赢不了墩」的主分牌兑现(`cashWinPoints`)

报障截图:♦ 作主、末家毙牌,玩家出 ♦K 而教练说「更好的是 ♦3 —— 最后一手,毙掉收分」。
**两处都错:**

* ♦K 和 ♦3 同为主、同为毙,那句理由对两张**同样成立** ——
  一条无法区分建议牌与实际牌的理由,本身就说明这条建议是错的;
* 真正的区别只有一个:♦K 多收 10 分。而 ♦K 上面压着 **14 张主**
  (大小王各 2、四门级数牌 8、♦A 2),排第 15,留在手里赢不了墩 ——
  期望大致是「一半贴给自己人、一半送给对手」。稳拿这墩时出它 = 确定的牌权 + 确定的 10 分。

`cheapSort` 里两张牌的排序键差 **9 级**,而 `cashPointW` 给 10 分的补偿是 **8 级** ——
差一口气就永远选不到它。**但没有去动那个常数**:v0.5.8 的标定没错,
错的是**拿牌序当未来价值的代理** —— 对一张上面压着 14 张的牌,这个代理彻底失真。
改成多生成一条候选,交给 `scorePlay` 用真正的 `futureValue` 比。

```
♦10(打10)   4/33 = 0.12  → 留着
♦3         30/33 = 0.91
```

### 甩牌只能甩整门 → 可以甩「压不住的那几组」(`throwBossSubset`)

需求列表里三条报障是同一个根因,就在候选生成的一行判据上:

```js
if(s!=='T'&&comps.length>=2&&bySuit[s].length<=6){
  const cl=classify(bySuit[s],trump);   // ← 只有【整门】
```

**AI 只会甩整门,从不甩子集。**于是:

* 「AI 不会撒对」—— ♣10♣10 和 ♣7♣7 都压不住,可手上还有一张带不动的 ♣ 小牌,
  整门就甩不成立,候选压根不生成;
* 「副色 AAK / AKK 不撒」—— 同理,♠A♠K♠K♠5 里 A 和 KK 各自都压不住,
  整门带上 ♠5 就废了;
* 「教练不能辨别撒牌比单张更大」—— 教练用同一套候选,集合里没有子集甩牌,
  只能拿单张去比,自然永远建议单张。

**为什么该甩:**一墩里「后出的牌结构必须和领出的一样才参与比较」([`docs/RULES.md`](RULES.md) E)。
分两次打两个对子,对手有**一个**主对就能端走一次;两对一起甩,他得同时有**两个**主对 ——
概率低得多。**牌型本身就是护甲。**

改法:生成「本门里所有压不住的组件」这个子集当候选。判据只用 `isBossPlay`,
不猜对手断不断门 —— 那归 `ruffable` 管,两件事不混在一起。
