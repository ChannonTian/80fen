# 更先进的做法:现在在哪一代、往上有什么、怎么够得着(2026-11-12)

产品方:我们研究过微软和腾讯的麻将 AI,但现在开发打牌 AI 的方法还不算先进;再看看有没有更好的方法,token 不够就先记下来以后做。
这一页是笔记和路线,**没有实现**。配套:[`external-ai-lessons.md`](external-ai-lessons.md)(11-08 的对照)、[`engine-direction.md`](engine-direction.md)(这次评估的全部数字)。

## 一、我们现在在哪一代

| 部件 | 我们的做法 | 属于哪一代 |
|---|---|---|
| 每一手怎么选 | 手写的一步打分(几十项、279 个开关) | 专家系统,最老的一代 |
| 往后看 | 剩 ≤ 12 张时抽样 20~60 个世界,用启发式自己续打到底 | 桥牌 / Skat 引擎 2000 年代的做法(PIMC)里较简的一种:续打不是精确解,也不是学出来的策略 |
| 读牌 | 硬断门 + 手写信号 + 几个拟合的小模型 | 同上,手工版 |
| 学习 | 窄决策上的逻辑回归;这次加了「真人选择」的条件 logit | Suphx 第一步(监督学习)的迷你版:几千手 vs 人家几千万手 |
| 目标 | 这次起:人机对照尺(同一副牌换座位) | 这一条是对的,和天凤段位是一个思路 |

**一句话:量具和纪律是好的,决策方法是上一代的。** 这次试的两样(价值网络、选择模型)方向对,但都卡在数据量上。

## 二、先进做法都长什么样

| 系统 | 游戏 | 核心 | 数据 / 算力 | 和我们的关系 |
|---|---|---|---|---|
| **Suphx**(微软亚研 2020) | 日麻 | 监督学习(人类高手牌谱)起步 → 自对弈强化学习;全局奖励预测;训练时看全知信息再逐步拿掉(oracle guiding);对局中用模拟微调策略 | 百万级人类牌谱 + 大规模 GPU | 配方最完整;我们没有人类牌谱的量 |
| **LuckyJ**(腾讯 2023) | 日麻 | ACH:演员-评论家 + 遗憾最小化,学混合策略(趋近均衡);加在线搜索 | 大规模 | 「不被摸透」那部分可借鉴;整体够不着 |
| **DouZero**(快手 2021) | 斗地主 | 深度蒙特卡洛:网络直接学「这个局面出这手,最后赢多少」,动作当输入;不搜索、不用人类数据 | 4 块显卡数天,10⁹~10¹⁰ 步 | 牌型结构和我们最像 |
| **PerfectDou**(2022) | 斗地主 | 「全知训练、不全知执行」:评论家看四家牌,演员只看自己;PPO | 10⁹ 步就胜过 DouZero 的 10¹⁰ 步 | 样本效率高一个量级 —— 我们算力少,该学这个 |
| **ShengJi+**(伯克利 2023) | **升级** | 深度蒙特卡洛,照 DouZero | 自对弈约 120 万局;只对随机出牌的基线验证过(升级率 97.6%);有开源代码 | **同一个游戏**(规则不是上海规则);证明这条路在升级上跑得通,没证明比强启发式强 |
| **Kermit + 策略推断**(阿尔伯塔 2019) | Skat(有主、算分的吃墩游戏) | 抽样世界 + 完全信息求解;**用学出来的策略给每个抽样世界算「他要是这手牌会不会这么打」的似然来加权** | 人类牌谱训练策略;CPU 即可 | 和我们现在的架构最接近的一步升级 |

共同点(也就是「先进」的定义):
1. **价值 / 策略由网络从对局结果里学**,不手写打分。
2. **海量对局**(10⁶~10¹⁰),所以模拟器必须快。
3. **训练看全知、执行不看**(oracle guiding / 全知评论家),把「知道牌就能做对」的那段差距变成训练信号。
4. 需要时再加搜索,搜索用的续打和读牌也是学出来的。

## 三、我们够不着的原因(都量过)

| 差什么 | 现状 | 需要 |
|---|---|---|
| 模拟器速度 | 现引擎自对弈约 0.7 秒 / 局 / 核(不开搜索);时间散在手写打分里,没有单一热点 | 每秒 10³ 局量级:精简内核 + 网络策略,不是优化现引擎 |
| 数据量 | 价值网络 M1 用 5.7k 局 → 误差 13.5 分,候选之间只差几分,排不过手写打分 | 至少 10⁶ 局 |
| 人类牌谱 | 约 300 局、8 位玩家 → 选择模型只学到「一般不拆对」,学不到「什么时候拆」;领出学像了但没变强 | 多两个量级才够监督学习当主力 |
| 算力 | 4 核、会被回收的容器 | 显卡若干天,或长时间 CPU |
| 运行环境 | 浏览器、单文件 | 网络权重量化后 1~5 MB,JS / WASM 前向,每手毫秒级 —— 这条不是障碍 |

## 四、路线(三档,按够得着的程度)

### 档 1:策略推断 + 快策略蒸馏(现有资源能做,最该先做)

- **做什么:**
  1. 把引擎自己的出牌**蒸馏**成一个快策略(条件 logit 或小网络;标签干净、数据要多少有多少)。真人座位另用牌谱拟合(这次的选择模型就是雏形)。
  2. **贝叶斯读牌:** 抽样世界按「这家如果拿这手牌,会不会像实际那样出」的似然加权,取代散落的手写读牌信号。对 AI 对手用蒸馏策略,对真人用真人策略。
  3. 快策略顺带当**续打**用(比现在的启发式续打快两个量级,世界可以多抽)。
- **为什么:** 这是 Skat 那条线上被反复验证的最大杠杆;zai-glm fork 我们时加权抽样也是正的;我们自己量过「全知排对 81%、抽样 68%」—— 读牌准一点,搜索就值钱一点。
- **需要:** 只要 CPU;复用这次的 `human-fit` 特征和拟合代码。
- **过关线:** 读牌校准(`calib-belief` 一类)变好;h2h / 池子 / 人机尺不负。
- **估计:** 1~2 个会话。

### 档 2:快速内核 + 模仿起步 + 全知评论家的自对弈强化学习(真正的「先进方法」)

- **第 0 步(两条路都要):快速内核。** 规则核(约 230 行:牌型拆解、跟牌合法性、一墩胜负、甩牌)移植成定长数组版本,和现引擎**逐位对拍**(`rules-vectors.js` + 随机对局)。语言二选一:纯 JS(浏览器和训练共用一份)或 Python / Rust(训练快,另导出)。
- **第 1 步:模仿。** 网络(动作当输入,牌用矩阵编码,出牌历史用序列编码 —— 照 DouZero / ShengJi+)先学现引擎的选择,**把 12 张内的搜索结果也当标签**(等于把搜索蒸馏进网络),再混入真人牌谱。目标:网络单独打 ≈ 现引擎,但快两个量级。
- **第 2 步:自对弈强化学习。** PPO 或深度蒙特卡洛;评论家看四家牌(PerfectDou 的做法,省一个量级样本);奖励用升级效用(全局奖励)。对手池里放现引擎和历史版本,防止只会打自己。
- **第 3 步:进浏览器。** 权重量化内嵌;收官仍可叠加搜索(续打换成网络)。
- **验收:** 还是那几把尺子,人机对照尺为主。
- **需要:** 一台带显卡的机器(自己的、租的,或 Kaggle / Colab 免费额度)跑若干天;4 核容器只够做第 0、1 步的开发和小规模验证。
- **估计:** 3~5 个会话的工程量;算力 100~300 显卡小时量级(有模仿起步,应比从零的 ShengJi+ / DouZero 少)。
- **风险:** 小算力下可能只追平现引擎(它已经吃了很多人工知识);上海规则的细节要自己写,ShengJi+ 的代码只能参考编码和训练设置。

### 档 3:均衡求解 / 在线子博弈搜索(LuckyJ 那一层)

四人、两两结盟的游戏里理论不保证,工程量大,**不建议**。只借一条便宜的:分差很小的候选之间随机,防被真人摸透。

## 四点五、ShengJi+ 能怎么用(11-12 看过代码,`github.com/TheMoon2000/shengji_plus`,2023-05 最后一次提交)

- **规模:** 约 4000 行 Python / PyTorch。`env/`(规则、牌集、观测编码)、`agents/`(DMC、DQN、随机、一个手写规则基线 `StrategicAgent`)、`networks/Models.py`、`TrainLoop.py`。
- **网络:** 打牌主网络 = 出牌历史过 LSTM(每墩 436 维 → 256)+ 约 1200 维局面与动作特征 → 768 宽的全连接,输出「这个局面出这手值多少」(动作当输入,DouZero 的做法)。亮主、扣底、炒地各有一个小网络。
- **奖励:** 用升级级数(闲家 ≥ 80 分 → 1 + (分 − 80) ÷ 40;40~79 → −1;1~39 → −2;0 → −3),和我们的 `levelUtility` 同构。扣底阶段另加了手写的引导奖励(鼓励扣断一门、不扣主)。
- **规则差异(没逐条核对):** 有「炒地」;抠底倍数按末墩赢家的牌型算;不是上海规则(没有造反 / 加固那一套)。打牌主体(两副牌、25 张、底 8 张、80 分上台、40 分一级)相同。
- **验证:** 只报了对随机出牌 97.7%;自带规则基线对随机约 807 : 193。**没有对强启发式的成绩。**
- **许可:** 仓库里没有 LICENSE 文件 → 只能读、学思路;代码和权重不能拷进我们的仓库或产品,要用得找作者授权。
- **当参照:** 可以,主要看三样 —— 观测 / 动作怎么编码、奖励怎么设、训练超参(`--discount 0.95 --epsilon 0.015 --games 2000 --enable-combos`)。
- **和我们的 AI 对弈:** 原理上可以(在我们的裁判下,写适配层:我们的局面 → 它的编码 → 它的网络给每个合法出法打分;只比打牌阶段;它在别的规则下练的,读数当下限)。
  **现在卡在权重:** 公开的 checkpoint(README 里的 `1180000.zip`)挂在作者个人网站的 http 链接上,本环境的代理只走 HTTPS,该站 HTTPS 502,下不下来。
  要产品方在自己电脑上试下载再传过来;没有权重就得自己训 120 万局,等于做档 2。
- **值不值得对一场:** 值。它直接回答档 2 最大的未知数 ——「从零自对弈 120 万局的网络,对我们手写 + 搜索的引擎是强是弱」。

### 对一场:适配层做完、自检过了,对局读数还没有(11-13)

**现状:** 这次任务本来要在本机做,实际落在了云端会话里 —— 权重还是下不来(该站 443 连不上;纯 http 云端代理不放行;Wayback 没存档)。
所以这一节只有**不依赖权重**的部分:适配层、张量对拍、规则核对、参照读数、速度。**三组对局和「对随机必须大胜」那项自检还没跑**,
在本机跑 `bash test/sjplus/run-local.sh`(约 1~2 小时,一条龙,任何一步不对就停),把 `../sjplus-ext/out/summary.txt` 发回来补这一节。
代码和复现说明在 [`test/sjplus/`](../../test/sjplus/README.md)。

**自检结果**

- **对局循环没写歪:** `match.js` 两边都放我们的引擎时,和 `ai-h2h.js` 同批种子的读数逐位相同(8 种子:2.50 ± 3.45 分)。
- **张量对拍通过(自检 A):** 我们引擎打的 30 副牌,在 ShengJi+ 自己的 `env/Game.py` 里一手一手重打,四个座位每一手都比:
  2143 手决策、42586 个「局面 × 候选」,它的环境编码出来的张量和适配层的**全部逐位相同**(带 oracle 的拼法另抽查 305 个,也相同)。
  两条路互不相通(它那边的未见牌、得分、每墩历史是它的引擎自己记的),所以牌名、花色、级牌、主、座位、得分、历史、未见牌、底牌这几项是对齐的。
  另有 9 手(领出 5 张以上的大甩牌)没比:它枚举跟法是组合爆炸的。
- **管线跑通:** 用随机权重把「Node 对局 ↔ Python 打分」、它自己环境里的评测、安全解包都跑过;随机权重的网络对 v0.7.67 是 −54 分/局(即网络没学到东西时的读数)。
- **还没做(要权重):** 在它自己的环境里对随机 / 对它的规则基线验权重(README:对随机 Level Rate 97.7%);我们的规则下对随机合法出牌必须大胜(脚本里的门槛:≥ +20 分/局 且 ≥ +0.4 级/局)。

**逐条核对出的规则差异(只比打牌阶段)**

| 项 | 它 | 我们 | 影响 |
| --- | --- | --- | --- |
| 单张 / 对子 / 拖拉机:合法领出、合法跟牌、一墩谁赢 | — | — | **没有差异。** 30 副里 519 个非甩牌墩赢家全同(末墩用终局总分核对);比过的 2143 手候选集合全同(含拖拉机子段、主里「A—副级牌—正级牌—小王—大王」相连) |
| 结算 | 80 上台、每 40 分一级;守住 <40 升 2、0 分升 3 | 同 | 没有 |
| **甩牌墩谁赢** | 引擎有毛病:同门、结构对得上的跟牌一律算赢过甩牌(不比大小)。30 副里 19 次成功的甩牌,它把 11 次判给了跟牌的人 | 甩成了就是赢墩,除非被主毙 | **中等,最要紧的一条。** 它等于没学过「甩牌是赢墩」:自己不会甩;对面甩时它可能当成自己这边赢的墩去处理。v0.7.67 每副每队甩 0.7 次 |
| 不给它甩牌(适配层的限制) | — | — | 小。我们自己的引擎被禁甩(改出其中最大一组)只亏 **1.96 ± 0.65 分 / 0.048 ± 0.015 级每局**(300 种子) |
| 甩牌失败 | 强制出那一组里最小的,训练时扣奖励 | 强制出被压住的最小一组,不罚分 | 没有(23 次甩牌、4 次失败,两边判得一样) |
| 抠底倍数 | 按末墩赢家最大的组件:单 2、对 4、两连对 16、更长 64 | 2 × 末墩领出张数 | 小。末墩是单张 / 对子时相同;30 副里终局总分全同。差在末墩是拖拉机 / 甩牌的局 |
| 亮主、反主、炒地、扣底 | 四个小网络自己做;有炒地(底牌和主可以易手) | 按 `ai-h2h.js` 定主定庄,扣底用我们的 `aiDiscard`;上海规则的造反 / 加固只在叫牌阶段 | 小。没有炒地、亮主者即庄家,都是它训练时见过的情形(炒地次数 0、首局抢庄);但它坐庄时手里的底不是它自己会扣的那种 |
| 级牌 | 2~A 随机 | 对局固定打 2 | 没有(在它的训练分布里) |

合起来:**它到我们的规则下会打折,读数是下限;折扣主要来自甩牌这一条**,不是来自打牌主体。
`run-local.sh` 里加了一组对照(`--opp-nothrow`:对面不许甩牌)量这条差异占多少 —— 我们的引擎为此让出约 2 分,所以两组读数一起看,真实差距夹在中间。

**同一把尺子上的参照(我们的规则,收官搜索关,不需要权重)**

| 对局 | 分/局 | 级/局 |
| --- | --- | --- |
| 随机合法出牌 对 v0.7.67 | −54.0 ± 2.0 | −0.925 ± 0.031 |
| 随机合法出牌 对 v0.5.7 | −52.1 ± 1.8 | −0.905 ± 0.032 |
| v0.5.7 对 v0.7.67(200 种子) | −10.7 ± 1.3 | −0.203 ± 0.025 |

「对随机」已经顶到头(两代引擎都是 +52~54 分),**分不出强弱** —— 它论文里唯一的成绩「对随机 97.7%」因此不说明它有多强,只说明不弱于会打牌。

**速度(给档 2;这台 4 核云端容器、纯 CPU,本机会重量一遍)**

- 主网络 276 万参数;一次前向 1.5 ms(batch 1)、10.9 ms(batch 32),单线程。
- 它自己的环境里一次打牌决策约 26 ms(每个候选单独前向一次);适配层里一次决策 = 编码 4~7 ms + 一批前向 6~10 ms。
- 训练口径的自对弈(四家都是网络、带甩牌和探索):**3.8 秒/局**(单进程单线程)。对比:我们的引擎四家自对弈 0.8 秒/局(搜索关)、2.4 秒/局(搜索开)。
- 它 README 的训练命令(6 个采样进程 + 学习):每进程单线程时 **约 3000 局/小时** → 它那 118 万局在这种机器上要 **16 天**;
  原样跑(每进程默认 4 线程挤 4 核)5 分钟一批(10 局)都学不完。
- 一局里网络前向和 Python 的规则 / 编码大约各占一半(估算:每手约 8 个候选 × 1.5 ms 对 26 ms)—— 所以档 2 的「快速内核」不是可选项:光换显卡,最多快一倍。

**对局读数出来以后怎么读(不超出数据)**

- **我们大胜**(它落在 v0.5.7 附近或更低,即对 v0.7.67 ≤ −10 分/局,且「对面不许甩牌」那组也差不多):
  照它的配方从零自对弈 118 万局,到不了手写 + 搜索的水平。档 2 不能照搬它,要靠模仿起步和更省样本的做法才有意义;优先级排在档 1 后面。
- **接近**(±3 分、±0.05 级以内):纯自对弈、没有任何人工知识,就能到我们现在的水平;再加模仿起步和收官搜索,有理由期待超过。档 2 值得投入,算力量级以它为参照(上面的 16 天是没有快速内核的上界)。
- **它更强**:对档 2 最强的支持;也说明我们的手写打分在前半局确实有系统性的缺口(和人机对照尺的结论同向)。它的权重没有许可证,用不了,只能自己训。
- 三种情况都要记得:读数是它的**下限**(规则折扣);只比了打牌阶段、级牌 2;它没有收官搜索,我们有 —— 所以「搜索关」那组更接近「网络 对 手写打分」的同类比较。

## 六、这次试验留给先进路线的教训

- **数据量差两个量级时,简单的赢。** 常数版「不拆对」三把尺子都过;拟合版只在对当前引擎和真人时为正,对老版本不行。
- **「更像真人」不等于「更强」。** 领出修正让一致率涨 4.5 个点,强度没涨,人机尺还略负。模仿只能给方向,强度要靠对局结果。
- **筛选读数要打折。** 小样本上挑最好的系数必然虚高(+2.54 → +1.49)。
- **前半局一手牌只差零点几分**,现场搜不出来,只能靠事先学 —— 这正是档 2 存在的理由。
